# Как подключить свой сервис к AUF ID

Страница для разработчиков сервисов экосистемы колледжа. Читается за десять минут, после них
можно писать код.

AUF ID — единый вход (SSO) по стандарту **OpenID Connect**. Ваш сервис не хранит пароли и не
делает форму входа: он получает от AUF ID подписанный токен и проверяет его **сам, локально**.
В AUF ID на каждый запрос ходить не нужно — в этом весь смысл.

---

## 1. Сначала определите, кто вы

От этого зависит всё остальное, и здесь чаще всего ошибаются.

| | **Сервер ресурсов** | **Клиент** |
| --- | --- | --- |
| Что делает | принимает запросы с готовым токеном и проверяет его | ведёт человека на страницу входа AUF ID и получает токен |
| Примеры | бэкенд-микросервис, API | браузерное приложение (SPA), лаунчер, серверное приложение со своими страницами |
| Нужна регистрация в AUF ID | **нет** | да, `client_id` выдаёт команда AUF ID |
| Есть секрет | нет | зависит от вида (см. §5) |
| Что читать дальше | §2, §3, §4 | §2, §3, §4 **и** §5 |

**Самое частое недопонимание.** Если вы пишете python-микросервис, за которым стоит браузерное
приложение, — вы **сервер ресурсов**, а не клиент. Клиентом является то приложение в браузере:
именно оно отправляет человека входить. Регистрировать микросервис не нужно, `client_id` и секрет
ему не положены.

---

## 2. Что проверять в токене

Сервис получает заголовок `Authorization: Bearer <access_token>`. Токен — это JWT, и проверить
нужно четыре вещи:

| Что | Как |
| --- | --- |
| **Подпись** | алгоритм `ES256`. Ключ берётся из `/oauth2/jwks` по полю `kid` из заголовка токена. Ключи кешируйте; пришёл незнакомый `kid` — перечитайте JWKS |
| **`iss`** | ровно адрес AUF ID, например `http://localhost:8080` |
| **`aud`** | `client_id` приложения, через которое человек вошёл — **см. врезку ниже** |
| **`exp`** | не истёк. Access token живёт **10 минут** |

Все адреса сервис узнаёт сам из документа обнаружения:

```
GET /.well-known/openid-configuration
```

Оттуда берутся `jwks_uri`, `issuer`, `authorization_endpoint`, `token_endpoint`, `userinfo_endpoint`.
**Не прописывайте их руками** — читайте из discovery, тогда переезд AUF ID на другой адрес вас
не затронет.

> ### Про `aud` — читайте внимательно
>
> В `aud` лежит `client_id` **приложения, которое запросило токен**, а не имя вашего
> микросервиса. Микросервис за планировщиком сверяет `aud` со `planner-dev` — тем клиентом,
> через который вошёл человек.
>
> Отсюда следствие, которое лучше узнать сейчас: **если за одним приложением стоит несколько
> микросервисов, один и тот же токен принимают все они.** Токен планировщика не примет соцсеть
> (у неё другой `aud`), но внутри планировщика разделения между микросервисами нет.
>
> Нужно развести права между своими сервисами — делайте это по **`scope`**. При регистрации
> клиента можно задать свои права вида `planner.read`, `notes.write`, и каждый сервис проверяет
> нужный ему.

**Писать проверку подписи вручную не нужно и не стоит.** Любая стандартная библиотека делает
всё сама, если указать issuer и audience.

### Пример на Python

```python
import jwt
from jwt import PyJWKClient

ISSUER = "http://localhost:8080"
AUDIENCE = "planner-dev"  # client_id приложения, а НЕ имя этого микросервиса

jwks = PyJWKClient(f"{ISSUER}/oauth2/jwks", cache_keys=True)

def verify(token: str) -> dict:
    key = jwks.get_signing_key_from_jwt(token).key
    return jwt.decode(
        token,
        key,
        algorithms=["ES256"],
        issuer=ISSUER,
        audience=AUDIENCE,
    )
    # Истёкший или поддельный токен -> исключение. Поймали -> отвечайте 401.
```

Для Java — стартер OAuth2 Resource Server и одна настройка:
`spring.security.oauth2.resourceserver.jwt.issuer-uri` (имя артефакта различается между Spring
Boot 3 и 4, смотрите по своей версии). Для Node.js — `jose` или `express-oauth2-jwt-bearer`.

## 3. Что лежит в access token

| Поле | Значение | Когда присутствует |
| --- | --- | --- |
| `sub` | **id пользователя (UUID)** — постоянный, не меняется никогда | всегда |
| `iss` | адрес AUF ID | всегда |
| `aud` | `client_id` приложения, запросившего токен | всегда |
| `scope` | выданные права, например `["openid", "profile", "email"]` | всегда |
| `iat`, `exp` | когда выдан и когда истекает | всегда |
| `roles` | `["ADMIN"]`, `["CURATOR"]`, `["STUDENT"]` или `[]` | **только в access token** |
| `name` | ФИО | если запрошен scope `profile` |
| `email` | почта | если запрошен scope `email` |
| `email_verified` | **всегда `false`**, см. §4 | если запрошен scope `email` |

`/userinfo` отдаёт те же `sub`, `name`, `email`, `email_verified` по тем же правилам — но
**на текущий момент**, а не на момент входа: профиль там собирается из базы пользователей.
Исправили человеку ФИО — следующий запрос к `/userinfo` вернёт новое, тогда как в выданном
ранее токене останется прежнее. Нужны свежие данные — спрашивайте `/userinfo`.

### Свои данные о пользователе храните по `sub`

`sub` — это UUID, он не меняется никогда. Почту человек может сменить, ФИО может быть исправлено.
**Не делайте почту первичным ключом** — это самая дорогая ошибка на этом этапе.

### Роли

Ролей три, и они намеренно крупные: `ADMIN`, `CURATOR`, `STUDENT`. Это общий словарь доступа —
по нему сервис решает, **пускать ли вообще**.

Всё, что тоньше — «этот куратор правит только свою группу», «этот студент видит только свои
заметки» — решает **ваш** сервис: только у него есть эти данные. В токен такие правила не кладём,
он бы раздувался и устаревал между выдачами.

Группы, кураторство и учебные данные в AUF ID **не живут** — это осознанная граница.

## 4. Подводные камни

Шесть вещей, которые иначе обнаружатся в коде, а не здесь.

1. **`email_verified` всегда `false`.** Опираться на него нельзя. Почту назначает администратор,
   а подтвердить владение ящиком нечем: писем AUF ID не отправляет. Поле есть только потому, что
   его требует стандарт.

2. **Заблокированный пользователь доживает до 10 минут.** При блокировке AUF ID удаляет выданные
   авторизации, но **уже выданный access token продолжает работать до истечения** — вы же
   проверяете подпись локально и в AUF ID не ходите. Если для какой-то операции 10 минут слишком
   много, напишите команде AUF ID: это решается через introspection.

   То же касается кражи refresh-токена: AUF ID её распознаёт и обрывает цепочку (повторно
   предъявленный токен отзывает доступ у обоих — и у вора, и у честного приложения, которому
   придётся заново провести человека через вход), но access-токены, выданные до этого, доживают
   свои 10 минут.

3. **Ротации ключа подписи нет.** В JWKS один ключ. Кешировать его можно и нужно, но «мягкой»
   смены не будет: если ключ заменят, все выданные токены станут недействительны разом. Это
   осознанное упрощение, ротация — следующая фаза.

4. **Лимит на выдачу токенов: 600 запросов в минуту с одного IP** на `POST /oauth2/token`.
   Превышение — `429` с заголовком `Retry-After`. Если ваш сервис за общим NAT, учитывайте это.

5. **Один токен на все микросервисы одного приложения** — см. врезку про `aud` в §2.

6. **AUF ID пока работает в одном экземпляре и без HTTPS.** Это про стадию разработки: на проде
   будет домен и TLS. Адрес не хардкодьте, читайте discovery.

## 5. Если вы клиент (ведёте человека на вход)

Поток один: **Authorization Code + PKCE** (`S256`, обязателен). Вид клиента определяет остальное —
его выбирает команда AUF ID при регистрации.

| Вид | Это про | Секрет | Refresh-токен |
| --- | --- | --- | --- |
| `NATIVE` | настольное или мобильное приложение, лаунчер | есть | **да**, 30 дней с ротацией |
| `BROWSER` | приложение в браузерной вкладке (SPA) | нет | нет, продление через `prompt=none` |
| `CONFIDENTIAL` | серверное приложение со своими страницами | есть | нет |
| `SERVICE` | сервис к сервису, без человека (`client_credentials`) | есть | нет |

### Как продлевать вход

**`NATIVE`** — refresh-токеном: `grant_type=refresh_token` на `/oauth2/token`. Срок 30 дней
отсчитывается **заново от каждого обновления**, то есть пока приложением пользуются, вход не
истекает. Токен **ротируется**: каждый обмен выдаёт новый, прежний сразу перестаёт работать —
не храните старый и не повторяйте запрос с ним. Класть refresh-токен в файл рядом с программой
не надо, для этого есть хранилище секретов операционной системы (Credential Manager, Keychain,
Secret Service).

**`BROWSER`** — «молчаливым продлением»: заход на `/oauth2/authorize` с параметром `prompt=none`.
Вошедшему AUF ID сразу вернёт новый код, не показывая форму; не вошедшему — ошибку
`login_required` на `redirect_uri`, по ней отправляйте человека входить по-настоящему.

> `prompt=none` учитывается **только если в запросе есть scope `openid`**. Без него параметр
> молча игнорируется, и не вошедший человек увидит форму входа вместо ошибки — это поведение
> стандарта, не наша особенность.

Два ограничения для `BROWSER`:

- **Скрытым iframe продлевать нельзя.** `/oauth2/authorize` отвечает `X-Frame-Options: DENY`
  (защита от clickjacking). Популярный приём «невидимый iframe для silent renew» здесь не
  заработает — нужен переход страницы или всплывающее окно.
- **Нужен CORS.** Код на токен вкладка меняет из JavaScript, поэтому ваш адрес должен быть в
  настройке `AUTH_CORS_ALLOWED_ORIGINS` на стороне AUF ID. Скажите команде свой origin.

### Адреса возврата (`redirect_uri`)

Сверяются **точно**, по списку — подставить свой адрес невозможно. Исключение одно: для
loopback-адресов (`http://127.0.0.1:<порт>`) **порт может быть любым**, а путь сверяется точно.
Настольное приложение может занимать свободный порт, dev-сервер фронтенда — слушать 5173 или
3000. Используйте `127.0.0.1`, не `localhost`.

## 6. Локальная разработка

```bash
docker compose up -d     # PostgreSQL + Redis
./mvnw spring-boot:run   # AUF ID на http://localhost:8080
```

При `AUTH_DEV_CLIENT_ENABLED=true` автоматически регистрируются два клиента:

| | Лаунчер | Планировщик |
| --- | --- | --- |
| `client_id` | `launcher-dev` | `planner-dev` |
| вид | `NATIVE` | `BROWSER` |
| секрет | `launcher-dev-secret` | нет |
| `redirect_uri` | `http://127.0.0.1:8090/login/oauth2/code/auth` | `http://127.0.0.1:5173/auth/callback` |

Общее: issuer `http://localhost:8080`, scopes `openid`, `profile`, `email`, PKCE обязателен,
экрана согласия нет.

Учётные записи заводит администратор через `POST /api/v1/admin/users` — саморегистрации нет.
В ответ приходит одноразовая ссылка активации, по ней человек задаёт пароль. Писем AUF ID не
отправляет.

Полное описание API — Swagger UI: http://localhost:8080/swagger-ui/index.html

### Проверить протокол руками

```bash
# 1. PKCE: секрет (verifier) и его хеш (challenge)
VERIFIER="verifier-$(openssl rand -hex 24)"
CHALLENGE=$(printf %s "$VERIFIER" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')

# 2. Открыть в браузере и войти. После входа браузер уйдёт на 127.0.0.1 — страница не откроется,
#    это нормально: скопируйте из адресной строки значение параметра code.
echo "http://localhost:8080/oauth2/authorize?response_type=code&client_id=launcher-dev&scope=openid%20profile%20email&redirect_uri=http://127.0.0.1:8090/login/oauth2/code/auth&state=xyz&code_challenge=$CHALLENGE&code_challenge_method=S256"

# 3. Обменять код на токены (код одноразовый, живёт несколько минут)
curl -s -X POST http://localhost:8080/oauth2/token \
  -u launcher-dev:launcher-dev-secret \
  -d grant_type=authorization_code \
  -d client_id=launcher-dev \
  -d redirect_uri=http://127.0.0.1:8090/login/oauth2/code/auth \
  --data-urlencode "code=ВСТАВЬТЕ_КОД" \
  --data-urlencode "code_verifier=$VERIFIER"

# 4. Посмотреть, что внутри access token (без проверки подписи, просто чтобы увидеть claims)
python3 -c "import sys,base64,json; p=sys.argv[1].split('.')[1]; \
print(json.dumps(json.loads(base64.urlsafe_b64decode(p + '=' * (-len(p) % 4))), indent=2, ensure_ascii=False))" \
  ВСТАВЬТЕ_ACCESS_TOKEN
```

## 7. Что нужно от команды AUF ID

Напишите, если вам нужно:

- **`client_id`** (и секрет, если вид клиента его предполагает) — скажите, что за приложение:
  браузерное, настольное, серверное или сервис-к-сервису, и какие адреса возврата;
- **свои `scope`** вида `planner.read` — если разводите права между своими микросервисами;
- **ваш origin в CORS** — если вы браузерное приложение;
- **тестовые учётки** с нужными ролями.

---

## Чего в AUF ID пока нет

Чтобы не ждать и не планировать под это: сброса пароля, двухфакторного входа (TOTP), личного
кабинета `/me`, журнала действий, introspection, рассылок на личные почты. Группы, кураторство и
учебные данные здесь не появятся никогда — это данные ваших сервисов.

Подробнее — `docs/Auth Service — архитектура SSO для экосистемы колледжа.md`, раздел «Порядок
работ до продакшна».
