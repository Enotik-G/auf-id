# AUF ID (репозиторий `auf-id`)

## ⚠️ Главное правило: код пишет Claude, но маленькими шагами и с объяснениями

**Claude пишет код сам — но по одному маленькому шагу за раз, и объясняет абсолютно всё доступным языком.** Пользователь учится Java/Spring, поэтому код, который он не понял, считается несделанным.

На каждом шаге Claude:

- **до кода** — коротко говорит, что делаем и зачем (какую проблему решаем);
- **пишет код** — один небольшой законченный кусок (одна миграция, один класс, одна настройка), а не пачку файлов;
- **после кода** — разбирает написанное построчно там, где есть что объяснять: каждая аннотация, каждое ключевое слово SQL, каждый нетривиальный выбор. Термины объясняет простыми словами при первом появлении, без жаргона без расшифровки;
- **проверяет** — собирает/запускает/смотрит в БД и показывает пользователю результат;
- **останавливается** и ждёт реакции, прежде чем идти дальше.

Не убегать вперёд: один шаг в одном сообщении. Если шаг получается большим — дробить.

Архитектурный документ в `docs/` предлагает «одна задача = одна сессия в Claude Code» — у нас задача дробится ещё мельче, как описано выше.

## Что это за проект и куда он растёт

Это **Auth Service** — единый OpenID-провайдер (SSO) колледжа. Сейчас цель — **минимально рабочая версия (MVP)**, но с прицелом на будущее: сервис должен стать **ядром внутренней цифровой экосистемы**.

- **Первые клиенты — лаунчер Minecraft и сервис планирования, оба делаются одновременно** (решение от 2026-10-08). Каждый в своём репозитории.
- Это не одна задача дважды: лаунчер — настольное приложение (вид клиента `NATIVE`, продлевает вход **refresh-токеном**); планировщик — **чисто браузерное приложение** с python-микросервисом за ним (вид `BROWSER`, продлевает вход заходом на `/oauth2/authorize` с `prompt=none`). Разбор — раздел 6 документа.
- **Python-микросервис планировщика клиентом не является** — он сервер ресурсов. Клиент тот, кто ведёт человека на страницу входа, то есть браузерное приложение. Микросервис только проверяет готовый токен: `jwks_uri` из discovery, подпись, `iss`, `aud`, `exp`. Регистрировать его в AUF ID не нужно.
- **Продлевать вход скрытым iframe нельзя:** `/oauth2/authorize` отвечает `X-Frame-Options: DENY` (умолчание Spring Security, менять не планируем). Только переход страницы или всплывающее окно. Закреплено тестом.
- **Дополнительного кода в Auth ни одному из них не требуется**: подключаются регистрацией клиента через админку.
- Примерно через год — другие учебные сервисы (meet, соцсеть, доска, заметки и т.д.).

**Решения по лаунчеру (2026-10-08):**

- вход — **системный браузер**, возврат на `http://127.0.0.1:<свободный порт>` (RFC 8252). Не встроенное окно: оно принадлежит лаунчеру, значит лаунчер может прочитать пароль (RFC 8252 §8.12). **Правок не требует** — Spring AS сам разрешает любой порт для loopback (проверено в `OAuth2AuthorizationCodeRequestAuthenticationValidator`), а наша проверка адреса в `AdminClientService` требует лишь «абсолютный, без фрагмента»;
- **refresh-токен — скользящее окно 30 дней** от последнего обновления, без общего предела: играешь — срок продлевается, забросил на месяц — вход заново. Готово (шаг 16);
- **виду `NATIVE` выдаётся секрет клиента**, хотя спрятать его в программе на чужом компьютере невозможно. Это не недосмотр: без секрета Spring отказывается обменивать refresh-токен — публичного клиента он опознаёт **только** по запросу с PKCE (`PublicClientAuthenticationConverter`), а в запросе на обновление PKCE нет. Альтернативой был свой `AuthenticationConverter` в пути аутентификации, что принципы безопасности ниже называют красным флагом. Защищает здесь PKCE, а не секрет; так же устроен поток Google для настольных приложений. Подробно — javadoc `ClientKind.NATIVE`;
- логин с паролем **внутри** лаунчера (ROPC) отвергнут: OAuth 2.1 этот поток удалил, Spring AS его не поддерживает, а свой писать запрещают принципы безопасности ниже.

**Путь пользователя (решение от 2026-10-07, отменяет саморегистрацию):** админ создаёт учётку → статус `INVITED` → одноразовая ссылка активации, которую админ передаёт студенту лично → студент задаёт пароль → `ACTIVE`.

**Писем сервис не отправляет** (шаг 7 выполнен): Mailpit, `spring-boot-starter-mail`, саморегистрация и подтверждение почты удалены, пакет `registration` снесён целиком. Подтверждать владение ящиком нечем — у студентов нет к ним доступа. Личные почты студентов и рассылки — **отдельные микросервисы** экосистемы, не AUF ID (решение 2026-10-10). **Входят только почты домена `sinhub.ru`** (решение 2026-10-10, отменяет «без ограничения» от 2026-09-29): `user/AllowedEmailDomains`, настройка `AUTH_ALLOWED_EMAIL_DOMAINS`; проверка при создании и смене почты, при входе (чужой домен неотличим от несуществующей почты) и для `BOOTSTRAP_ADMIN_EMAILS`. Ящики — только логин.

**Сервис называется AUF ID**: пакет `ru.auf.id`, артефакт `auf-id`, репозиторий `auf-id` (шаг 8 выполнен). Префикс настроек остался `auth.` — он описывает предметную область, а не продукт, и менять его значило бы ломать все существующие `.env` без пользы.

Ключевая идея архитектуры: Auth выдаёт короткоживущий JWT (10 мин), остальные сервисы проверяют подпись локально по JWKS и **не ходят в Auth на каждый запрос**. Поэтому новый сервис подключается к экосистеме без правок в самом Auth — только регистрацией клиента.

### Требования к коду

- **Читаемость важнее краткости.** Понятные имена, без магии и хитрых трюков; код должен читаться человеком, который учит Spring.
- **Масштабирование закладываем сразу, но без переусложнения:** stateless-приложение (состояние — в БД/Redis, не в памяти), чёткое разделение на слои (controller → service → repository), зависимости через интерфейсы там, где реально будут разные реализации. Не строить абстракции «на всякий случай».
- **MVP, а не всё сразу:** делаем фазу 1 из документа, фазы 2–3 — только когда дойдём.

### Осознанные отступления от `docs/`

Документ писался под другой стек. Это **не ошибки, которые надо чинить**:

- **Maven**, а не Gradle.
- **Liquibase**, а не Flyway.
- **Нет таблицы `allowed_email_domains`** — разрешённые домены (`sinhub.ru`) задаются настройкой `AUTH_ALLOWED_EMAIL_DOMAINS`.
- **Параметры БД (`DB_NAME`, `DB_USER`, `DB_PASSWORD`) — в `.env`**, умолчаний нет: репозиторий публичный, и пароль лежал в `compose.yaml` открытым текстом.

### Перец для паролей (`PASSWORD_PEPPER`)

Секрет, который подмешивается к паролю перед Argon2id (`user/PasswordHasher`). **Умолчания нет намеренно**: без переменной приложение падает с `Could not resolve placeholder 'PASSWORD_PEPPER'`, короче 32 символов — отказывается стартовать. Так прод не сможет случайно запуститься с «учебным» перцем из репозитория.

- **Локально — файл `.env` в корне проекта** (в `.gitignore`, права `600`), его подхватывает `spring.config.import=optional:file:.env[.properties]` при любом способе запуска (IntelliJ, `./mvnw spring-boot:run`). Содержимое: `PASSWORD_PEPPER=<openssl rand -base64 48>`. На новой машине — создать заново.
- На сервере `.env` нет → берётся переменная окружения; нет и её → приложение не стартует.
- **Сменить перец = все существующие пароли перестанут подходить**, поэтому он постоянный для каждого окружения.
- Тесты задают свой перец сами (`AufIdApplicationTests`, `PasswordHasherTest`), переменная им не нужна.

## Подводные камни (уже наступали)

- **`formLogin().loginPage("/login").permitAll()` открывает только `/login` без параметров** — `/login?error` и т.п. отправляли обратно на `/login`, сообщения не показывались. Страница входа открыта в `authorizeHttpRequests` (`requestMatchers("/login")` сравнивает только путь).
- **MockMvc: `.param("x", "")` ≠ `?x` в адресе.** Правила Spring Security могут смотреть на строку запроса, а `.param` её не заполняет. Проверять адреса с параметрами как в браузере: `get("/login?error")`.

- **Postgres 18 сменил расположение данных.** Том монтируется в `/var/lib/postgresql`, **не** в `/var/lib/postgresql/data`. Внутри Postgres сам делает подпапку `18/docker`. Со старым путём контейнер отказывается стартовать.
- **Группа `docker` применяется только при новом входе в систему.** Причём в GNOME недостаточно перелогиниться: `gnome-terminal-server` наследует группы от `systemd --user`, который переживает выход. Нужна полная перезагрузка (или `newgrp docker` — но только для одного окна).
- **Системный PostgreSQL 17 был отключён** (`sudo systemctl disable --now postgresql`), он занимал порт 5432. Данные его целы в `/var/lib/postgresql/17/main`.
- **Настройка новой машины:** нужны JDK 25 (`openjdk-25-jdk`), `docker.io`, `docker-compose`, и пользователь в группе `docker`.

## Работа с БД

Схемой управляет **только Liquibase**. `spring.jpa.hibernate.ddl-auto=validate` — Hibernate ничего не создаёт и не правит, только сверяет `@Entity` со схемой при старте. Значения `update`, `create`, `create-drop` использовать **нельзя**: получатся два хозяина у одной схемы.

### Структура миграций

```
src/main/resources/db/changelog/
├── db.changelog-master.yaml      # только include'ы, путь от корня classpath
└── changes/
    └── 001-create-users.sql      # сами миграции — на SQL
```

Master — в YAML (Spring Boot ищет именно этот путь по умолчанию). Сами миграции — **на чистом SQL**, а не в абстракциях Liquibase: проект навсегда на Postgres, а нужны `jsonb`, `uuidv7()`, частичные индексы — в YAML это не выразить.

Формат SQL-файла:

```sql
--liquibase formatted sql

--changeset enotik:001-create-users
CREATE TABLE ...;
```

### Железное правило

**Применённый changeset не правят никогда.** Liquibase хранит его контрольную сумму в `databasechangelog`; при расхождении приложение откажется стартовать. Нужна правка — новый changeset.

Если changeset **упал** — он выполняется в транзакции, откатывается целиком и в журнал не попадает. Можно спокойно исправить файл и запустить заново.

### Соглашения по схеме

- Первичные ключи — `uuid` с `DEFAULT uuidv7()` (нативная функция Postgres 18: индекс не фрагментируется, в отличие от случайного v4).
- Время — **только `timestamptz`**, никогда `timestamp`.
- Перечисления — `varchar` + именованный `CHECK`, **не** нативный `ENUM` (из ENUM невозможно удалить значение).
- Все ограничения именуем: `CONSTRAINT users_status_check CHECK (...)`.
- `NOT NULL` по умолчанию; `NULL` разрешаем только там, где есть легальное состояние «значения нет».

- **Лимиты по IP и NAT.** Если пользователи за общим NAT (сеть колледжа), они делят одно ведро. Поэтому вход — 300/мин (`AUTH_LOGIN_RATE_LIMIT`), в тестах — 20 (`src/test/resources/config/application.properties`), чтобы тест лимита не гонял 300 входов через Argon2.
- **Первый администратор** (`BootstrapAdminGranter`) — роль из `BOOTSTRAP_ADMIN_EMAILS` выдаётся при входе **только пока нет ни одного действующего админа** (2026-10-10), иначе снятая роль возвращалась бы.
- **Сроки токенов** — только в `authserver/TokenLifetimes` (10 мин, 30 дней); память о погашенных refresh-токенах ссылается на тот же срок. Менять — вместе с `docs/service-integration.md`.
- **Пароль** — `provisioning/PasswordPolicy`: 12–128 символов (code points), не из `passwords/common-passwords.txt` (~46 тыс. паролей от 12 символов из SecLists, MIT).
- **Согласие на ПДн** — при активации, в одной транзакции с паролем (`consent/ConsentService`, таблица `consents`). Текст — черновик `templates/consent/personal-data.html`; поменяли текст — поднять `auth.consent.personal-data-version`.
- **Redis хранит не только временное:** реестр погашенных refresh-токенов на 30 дней. На сервере — с сохранением на диск.
- **Лимиты по IP берут `request.getRemoteAddr()`** — и за прокси это адрес прокси, а не человека. Решено шагом 20 настройками, без правок кода: `FORWARD_HEADERS_STRATEGY=native` (Tomcat сам подменяет адрес из `X-Forwarded-For`) и `TRUSTED_PROXIES` — от кого этот заголовок принимать. **Оба умолчания выключают механизм намеренно** (`none` и только loopback): доверять заголовку без прокси нельзя, его прислал бы сам клиент, а умолчание Tomcat доверяет всем частным сетям, то есть в Docker — любому контейнеру.
