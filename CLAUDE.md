# Auth Service (репозиторий `planner`)

## ⚠️ Главное правило: код пишет Claude, но маленькими шагами и с объяснениями

**Claude пишет код сам — но по одному маленькому шагу за раз, и объясняет абсолютно всё доступным языком.** Пользователь учится Java/Spring, поэтому код, который он не понял, считается несделанным.

На каждом шаге Claude:

- **до кода** — коротко говорит, что делаем и зачем (какую проблему решаем);
- **пишет код** — один небольшой законченный кусок (одна миграция, один класс, одна настройка), а не пачку файлов;
- **после кода** — разбирает написанное построчно там, где есть что объяснять: каждая аннотация, каждое ключевое слово SQL, каждый нетривиальный выбор. Термины объясняет простыми словами при первом появлении, без жаргона без расшифровки;
- **проверяет** — собирает/запускает/смотрит в БД и показывает пользователю результат;
- **останавливается** и ждёт реакции, прежде чем идти дальше.

Не убегать вперёд: один шаг в одном сообщении. Если шаг получается большим — дробить.

Архитектурный документ в `docs/` предлагает «одна задача = одна сессия в Claude Code» — у нас задача дробится ещё мельче, как описано выше.

## Что это за проект и куда он растёт

Это **Auth Service** — единый OpenID-провайдер (SSO) колледжа. Сейчас цель — **минимально рабочая версия (MVP)**, но с прицелом на будущее: сервис должен стать **ядром внутренней цифровой экосистемы**.

- Первым клиентом будет **сервис планирования** — его начнём делать чуть позже (стек ещё не выбран; отдельный репозиторий).
- Примерно через год — много других учебных сервисов (meet, соцсеть, доска, заметки и т.д.).

**Сервисом пользуются не только студенты колледжа.** Регистрация открыта для **любой почты** — главное, чтобы владелец её подтвердил (ссылка из письма). Ограничения по домену колледжа **нет** (решение от 2026-09-29, отменяет задачу «allowlist доменов» из документа). Путь пользователя: саморегистрация (почта + пароль) → письмо со ссылкой → подтверждение → `ACTIVE`. Приглашения по CSV остаются дополнительным путём для колледжа.

Ключевая идея архитектуры: Auth выдаёт короткоживущий JWT (10 мин), остальные сервисы проверяют подпись локально по JWKS и **не ходят в Auth на каждый запрос**. Поэтому новый сервис подключается к экосистеме без правок в самом Auth — только регистрацией клиента.

### Требования к коду

- **Читаемость важнее краткости.** Понятные имена, без магии и хитрых трюков; код должен читаться человеком, который учит Spring.
- **Масштабирование закладываем сразу, но без переусложнения:** stateless-приложение (состояние — в БД/Redis, не в памяти), чёткое разделение на слои (controller → service → repository), зависимости через интерфейсы там, где реально будут разные реализации. Не строить абстракции «на всякий случай».
- **MVP, а не всё сразу:** делаем фазу 1 из документа, фазы 2–3 — только когда дойдём.

### Осознанные отступления от `docs/`

Документ писался под другой стек. Это **не ошибки, которые надо чинить**:

- **Maven**, а не Gradle.
- **Liquibase**, а не Flyway.
- **Нет allowlist доменов и таблицы `allowed_email_domains`** — принимаем любую почту, фильтр — подтверждение владения ящиком.
- **Нормализация email — только `trim` + нижний регистр.** Документ предлагает ещё срезать `+alias`, но это верно только для Gmail и некоторых провайдеров; для произвольных почт так делать нельзя.
- **Саморегистрация** — в документе вход только по приглашению.
- **Redis пока не поднимаем** — понадобится на задаче про rate limiting. ⚠️ Из-за открытой регистрации rate limit обязателен **до** того, как сервис станет доступен снаружи.
- **Email хранится открытым текстом.** В документе он зашифрован + `email_hash`, но само шифрование там отнесено к фазе 2 (нужен Vault). Приедет отдельной миграцией.

### Перец для паролей (`PASSWORD_PEPPER`)

Секрет, который подмешивается к паролю перед Argon2id (`user/PasswordHasher`). **Умолчания нет намеренно**: без переменной приложение падает с `Could not resolve placeholder 'PASSWORD_PEPPER'`, короче 32 символов — отказывается стартовать. Так прод не сможет случайно запуститься с «учебным» перцем из репозитория.

- Сгенерировать: `openssl rand -base64 48`.
- Локально — один раз сгенерировать и сохранить (например, в Run Configuration IntelliJ → Environment variables). **Сменить перец = все существующие пароли перестанут подходить**, поэтому он постоянный для каждого окружения.
- Тесты задают свой перец сами (`PlannerApplicationTests`, `PasswordHasherTest`), переменная им не нужна.

## Подводные камни (уже наступали)

- **Postgres 18 сменил расположение данных.** Том монтируется в `/var/lib/postgresql`, **не** в `/var/lib/postgresql/data`. Внутри Postgres сам делает подпапку `18/docker`. Со старым путём контейнер отказывается стартовать.
- **Группа `docker` применяется только при новом входе в систему.** Причём в GNOME недостаточно перелогиниться: `gnome-terminal-server` наследует группы от `systemd --user`, который переживает выход. Нужна полная перезагрузка (или `newgrp docker` — но только для одного окна).
- **Системный PostgreSQL 17 был отключён** (`sudo systemctl disable --now postgresql`), он занимал порт 5432. Данные его целы в `/var/lib/postgresql/17/main`.
- **Настройка новой машины:** нужны JDK 25 (`openjdk-25-jdk`), `docker.io`, `docker-compose`, и пользователь в группе `docker`.

## Работа с БД

Схемой управляет **только Liquibase**. `spring.jpa.hibernate.ddl-auto=validate` — Hibernate ничего не создаёт и не правит, только сверяет `@Entity` со схемой при старте. Значения `update`, `create`, `create-drop` использовать **нельзя**: получатся два хозяина у одной схемы.

### Структура миграций

```
src/main/resources/db/changelog/
├── db.changelog-master.yaml      # только include'ы, путь от корня classpath
└── changes/
    └── 001-create-users.sql      # сами миграции — на SQL
```

Master — в YAML (Spring Boot ищет именно этот путь по умолчанию). Сами миграции — **на чистом SQL**, а не в абстракциях Liquibase: проект навсегда на Postgres, а нужны `jsonb`, `uuidv7()`, частичные индексы — в YAML это не выразить.

Формат SQL-файла:

```sql
--liquibase formatted sql

--changeset enotik:001-create-users
CREATE TABLE ...;
```

### Железное правило

**Применённый changeset не правят никогда.** Liquibase хранит его контрольную сумму в `databasechangelog`; при расхождении приложение откажется стартовать. Нужна правка — новый changeset.

Если changeset **упал** — он выполняется в транзакции, откатывается целиком и в журнал не попадает. Можно спокойно исправить файл и запустить заново.

### Соглашения по схеме

- Первичные ключи — `uuid` с `DEFAULT uuidv7()` (нативная функция Postgres 18: индекс не фрагментируется, в отличие от случайного v4).
- Время — **только `timestamptz`**, никогда `timestamp`.
- Перечисления — `varchar` + именованный `CHECK`, **не** нативный `ENUM` (из ENUM невозможно удалить значение).
- Все ограничения именуем: `CONSTRAINT users_status_check CHECK (...)`.
- `NOT NULL` по умолчанию; `NULL` разрешаем только там, где есть легальное состояние «значения нет».

Заметки к задаче:

- `full_name` в `users` — `NOT NULL`, значит ФИО спрашиваем прямо в форме регистрации.
- Приглашённые (`INVITED`) и самостоятельно зарегистрированные (`PENDING_VERIFICATION`) — разные статусы: у них разный путь к `ACTIVE`.
- Время в коде — через бин `Clock` (`Instant.now(clock)`), а не `Instant.now()`: так в тестах можно подставить нужный момент (`Clock.fixed`).
- Занятая почта при регистрации — молча ничего не делаем (защита от перебора «чья почта зарегистрирована»). Позже: письмо владельцу «кто-то пытался зарегистрироваться на ваш адрес» и повторная отправка письма подтверждения, если ссылка истекла.
- Ответ 400 на ошибки валидации пока общий (`Invalid request content.`), без указания поля — доработать, когда появится фронтенд.
- Гонка при регистрации одной почты: `existsByEmail` пройдут оба запроса, второго остановит `users_email_key` → `DataIntegrityViolationException`. Сервис должен это обработать.
